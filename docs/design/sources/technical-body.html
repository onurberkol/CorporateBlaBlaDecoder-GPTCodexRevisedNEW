Dokümanın okunma sırası

Önce inşa hikâyesini (hangi sırayla, neden) okuyun — bu, kod tabanının zihinsel haritasını verir. Sonra mimari değişmez kuralı içselleştirin; kod tabanındaki hemen her güvenlik kararı oradan türer. Ardından modüller (core → functions → firestore → mobile → pipeline → admin) sırayla, her birinin gerçek kod alıntılarıyla. En sonda güvenlik tehdit modeli, dağıtım/devir adımları ve "sesi yeniden ayarlama" operasyon kılavuzu var.

İnşa hikâyesi: hangi sırayla ve neden

Proje rastgele bir sırayla yazılmadı. Her adım bir öncekinin üstüne, bilinçli bir bağımlılık mantığıyla kuruldu. Devralan yazılımcının kod tabanını "neden böyle bölünmüş" diye sorgulamadan anlaması için, izlediğimiz yolu olduğu gibi aktarıyorum.

0
Fikir ve sesin sabitlenmesi (kod öncesi)
Beyaz yakalı komütçü analiziyle başladık; viral yakıtın kurumsal frustrasyon olduğuna karar verdik. Kritik karar: kod yazmadan önce "ses"i sabitledik — Decoder ve Composer için TR/EN altın few-shot örneklerini elle yazdık. Çünkü ses, stack'ten bağımsız ve kopyalanamaz olan kısım; iskeleti boş kutuya kurmamak için önce o netleşmeliydi.
1
IP çekirdeği — packages/core
İlk yazılan kod. Tip sözleşmeleri, ton tanımları, few-shot kütüphaneleri ve iki system-prompt builder. Firebase yok, React Native yok — saf IP. Neden ilk: hem proxy hem app bunu tüketecek; tek doğruluk kaynağı burada olmalı.
2
Cloud Function proxy — functions
core'u tüketen ilk gerçek tüketici. Claude anahtarını tutan, kotayı ve premium gating'i uygulayan tek yer. Mimari değişmez kural burada hayata geçti: anahtar client'ta asla yok.
3
Expo iskeleti — apps/mobile
Expo Router, 4 sekme, Reanimated Ton Kadranı, react-native-view-shot paylaşım-kartı motoru. Onaylanan kâğıt/mürekkep/damga estetiği theme.ts'te token'a dönüştü. App backend'e yalnızca proxy üzerinden konuşur.
4
Firebase + RevenueCat + bildirimler
Anonim Auth, Firestore şeması + güvenlik kuralları, RevenueCat webhook'u (tier'ı yazan tek kaynak), paywall, ve commute-timed yerel bildirimler.
5
Günlük Plaza pipeline — content-pipeline
Günlük kartları canlı API'ye bağlamadık (maliyet + tutarlılık). Claude ile aylık batch üretip dailyPlaza/{date}'e yazan tsx CLI. App sadece günün kartını çeker.
6
Mağaza hazırlığı + Admin
İkonlar (sharp ile), EAS profilleri, locale-aware yasal sayfalar, ASO metadata, submission checklist; ardından Next.js admin paneli (sunucu-taraflı Admin SDK, HMAC şifre kapısı, Plaza editörü).
7
Dört özellik dalgası
Dalga 1: Arşiv + Haftalık Karne + premium savunma. Dalga 2: Ton Hafızası (persona — core tipi + prompt enjeksiyonu + sunucu gating). Dalga 3: App Check + analytics + crash/ErrorBoundary. Dalga 4: Paylaşım kartı QR + erişilebilirlik geçişi.
8
QA turları + isim güncellemesi
Typecheck, syntax, davranış testleri, import çözümleme, string/tema/export denetimleri. Son olarak TR ürün adı her yerde "Corporate BlaBla Decoder" olarak güncellendi (US "Per My Last Email" korundu).
Taşıyıcı ilke: bağımlılık sırası. core (kimseye bağlı değil) → functions (yalnızca core'a) → mobile (core + proxy'ye) → pipeline/admin (core + Firestore'a). Bu sıra, her adımın bir öncekini sağlam bir zemin olarak kullanmasını sağladı.

Mimari ve değişmez kural

Tüm sistem tek bir cümle etrafında kurulur ve devralan herkesin bunu ezbere bilmesi gerekir:

Mimari değişmez kural

(1) Claude API anahtarı client'ta asla bulunmaz — yalnızca Cloud Function proxy'sinde. (2) users.tier (premium gerçeği) yalnızca RevenueCat webhook'u tarafından yazılır. (3) Kota ve premium gating yalnızca sunucuda uygulanır; firestore.rules istemcinin tier/usage'a dokunmasını engeller.

Tehdit modeli — neden böyle

Mobil istemci düşman varsayılır. Birisi APK'yı tersine çevirebilir, istekleri taklit edebilir, kendi Firestore yazımlarını deneyebilir. Bu üç kural tam da bu senaryolara karşı:

Neden anonim auth? Çünkü sürtünme viralitenin düşmanı — hesap zorlaması dönüşümü öldürür. Ama proxy'nin yine de istek başına bir kimliğe ihtiyacı var (kota, tier). Monorepo ve build topolojisi

npm workspaces kullanıyoruz (kök package.json içinde "workspaces": ["packages/*","apps/*","admin"]). Paylaşılan IP (packages/core) hem proxy hem app tarafından import edilir.

corporate-blabla/
├── packages/core/        # IP: types, tones, fewshot, prompt builder'lar
│   └── src/{types,tones,plaza,index}.ts · prompts/{decoder,composer}.ts · fewshot/*.{tr,en}.ts
├── functions/            # Firebase v2 Cloud Functions (esbuild ile core'u bundle'lar)
│   └── src/{config,quota,anthropic,validate,decode,compose,plaza,revenuecat,reengage}.ts
├── apps/mobile/          # Expo SDK 54 · Expo Router
│   └── app/* · src/{theme,lib/*,components/*} · app.json · eas.json
├── content-pipeline/     # tsx CLI: Claude → dailyPlaza/{date}
├── web/                  # Firebase Hosting: index + privacy/terms (EN) + gizlilik/kullanim (TR)
├── admin/                # Next.js 15 admin (server-side Admin SDK)
├── firestore.rules · firestore.indexes.json
└── firebase.json         # functions (predeploy build) + hosting (cleanUrls, /kvkk rewrite)

Kritik build kararı: functions neden core'u esbuild ile bundle'lar

Firebase yalnızca functions/ klasörünü zipleyip deploy eder ve orada npm install çalıştırır. packages/core bu klasörün dışında olduğu için, normal bir import '@corporate-blabla/core' deploy'da çözülemezdi. Çözüm: predeploy adımında esbuild, core'u fonksiyon bundle'ının içine inline eder. Ağır SDK'lar (firebase-admin, firebase-functions, @anthropic-ai/sdk) external bırakılır (bulutta normal kurulur); yalnızca kendi kodumuz ve core inline edilir. firebase.json içindeki predeploy: ["npm --prefix functions run build"] bunu tetikler.

Devralırken dikkat: core'da bir değişiklik yaptıysan, functions'ı yeniden deploy etmeden önce npm --prefix functions run build çalıştır — aksi halde eski inline core deploy edilir.

packages/core — kopyalanamaz IP

Bu paket ürünün ruhudur ve kasıtlı olarak stack-agnostiktir: Firebase'e, React Native'e, hiçbir runtime'a bağlı değildir. Hem proxy hem app çıktı sözleşmesini buradan paylaşır. Few-shot havuzu da burada — modelin herkeste aynı olduğu bir dünyada, asıl moat budur.

1 · Çıktı sözleşmesi (types.ts)

Modele, bu şekillere birebir uyan JSON döndürmesi söylenir; app aynı şekillere karşı parse eder. Tasarım kararı: nesne anahtarları İngilizcedir (kod için sabit, locale değişse de değişmez); değerler kullanıcının diline lokalizedir. Bu, i18n eklemeyi kodun şeklini bozmadan mümkün kılar.

packages/core/src/types.ts
export type Locale = 'tr' | 'en';
export type ToneId = 'kind' | 'distant' | 'surgical' | 'boss';
export const TONE_ORDER: ToneId[] = ['kind','distant','surgical','boss']; // kadran sırası

export interface DecoderResult {
  translation: string;                         // düz, bıçak gibi tercüme
  meter: number;                               // pasif-agresiflik 0–100
  traps: { phrase: string; meaning: string }[];// 1–3 tuzak
  defense?: string;                            // premium "savunma önerisi"
}
export interface ComposerResult {
  intent: string;
  variants: Record<ToneId, string>;            // her ton için bir yeniden-yazım
}
export interface ComposePersona {              // premium "ton hafızası"
  name: string; kind: 'self' | 'recipient'; samples: string[];
}

2 · Tonların kişiliği ve mizah ölçeği (tones.ts)

Dört ton bir TONES haritasında tanımlıdır. Her tonun bir direction metni vardır — kadranın kişiliği burada yaşar ve Composer prompt'una aynen enjekte edilir. Tonu yeniden ayarlamak, kodun başka yerine dokunmadan bu metni değiştirmektir. FREE_TONES tek bir yerden türer, böylece UI ve proxy aynı gerçeği paylaşır: surgical ve boss premium, kind ve distant ücretsiz.

Metre bandı modelden gelmez — meter'dan istemci-tarafında türetilir. Bu fonksiyonun eşiklerini kaydırmak, tüm uygulamayı topyekûn daha acımasız ya da daha ölçülü yapar. Bu yüzden "ürünün mizah ölçeği" odur:

packages/core/src/tones.ts
export function meterBand(meter: number): MeterBand {
  if (meter <= 30) return 'innocent';   // masum: gerçekten nötr
  if (meter <= 60) return 'sneaky';     // sinsi: sessiz bir kenar, hafif baskı
  if (meter <= 85) return 'evidence';   // kanıt-bırakan: "belirttiğim üzere"
  return 'nuclear';                     // nükleer: loop'a alma, açık eskalasyon
}
export const FREE_TONES: ToneId[] =
  TONE_LIST.filter((t) => !t.premium).map((t) => t.id);   // → ['kind','distant']

3 · Few-shot kütüphaneleri (fewshot/*) — asıl moat

Decoder ve Composer için TR ve EN ayrı ayrı, elle küratörlenmiş örnekler. Mevcut sayılar: Decoder TR 10 / EN 9, Composer TR 3 / EN 3 senaryo (her senaryo dört tonu içerir). En kritik karar: EN setleri çeviri değil, transcreation. "Rica etsem"in İngilizce karşılığı yoktur; onun yerine "per my last email", "for visibility", "bandwidth", "happy to discuss" vardır. İki ayrı küratörlük, iki ayrı moat. Model herkeste aynı; ses bu dosyalarda.

Sesi keskinleştirmek: bu dosyalara örnek ekle/değiştir. Tercümeleri kısa ve bıçak gibi tut; mizah doğruluktan gelmeli, abartıdan değil. Set başına ~10-12 örnek idealdir — bağlamak için yeter, prompt'u şişirmeyecek kadar az.

4 · Decoder prompt'u — katı JSON sözleşmesi (prompts/decoder.ts)

Builder, locale'e göre ses kurallarını, metre kalibrasyonunu ve few-shot örneklerini bir araya getirir; modelden tek bir katı-JSON nesnesi döndürmesini ister. Prompt'un kalbi şu (gerçek metinden):

buildDecoderSystemPrompt(locale, withDefense) — çıktı kuralları
# Your voice
- Short and scalpel-like. The translation is a diagnosis, not an essay.
- The humor comes from being TOO ACCURATE, never from exaggeration.
- Never moralize, never soften. Write every value in {Turkish|English}.

# The meter (0-100, integer)
0-30 innocent · 31-60 sneaky · 61-85 evidence · 86-100 nuclear
Most real corporate messages land 45-85. Reserve 90+ for genuine escalation.

# Output format — CRITICAL
Return ONLY a single JSON object. No markdown, no fences, no preamble.
{ "translation": string, "meter": int, "traps": [{ "phrase", "meaning" }] }

Few-shot örnekleri prompt'un sonuna INPUT: … / OUTPUT: {…json…} biçiminde eklenir. withDefense=true (yalnızca premium) olduğunda şemaya bir defense alanı ve onu üreten bir talimat eklenir — gating prompt seviyesinde de uygulanır.

5 · Composer prompt'u — dört ton tek çağrı + persona (prompts/composer.ts)

Tasarım kararı: Composer dört tonu tek çağrıda üretir. Böylece kullanıcı kadranı kaydırırken yeni bir istek atılmaz — sıfır gecikme, sıfır ekstra maliyet. Ton hafızası (persona) verildiğinde, prompt'a bir "tone memory" bloğu enjekte edilir; örnekler asla aynen kopyalanmaz, yalnızca dört tonun register'ını modüle eder:

packages/core/src/prompts/composer.ts — personaBlock
function personaBlock(persona: ComposePersona, locale: Locale): string {
  const samples = persona.samples.map((s) => `  • ${s}`).join('\n');
  return `
# Personalization (tone memory)
The user trained "${persona.name}". Here is how that person writes:
${samples}
Subtly adapt the register, formality, directness and vocabulary of ALL
FOUR variants — but NEVER copy the samples verbatim.`;
}
